# UX Review Principles

When a flow feels awkward but the reason is unclear, walk the seven principles and name the one whose check fails.

| Principle | Definition | Violation on screen | Evidence case | Check | Typical fix |
|---|---|---|---|---|---|
| Action authority | Show a destructive primary action only to the role authorized to perform it. | A general team member can see or invoke a control that removes all team support. | [oss-hub #1151](https://github.com/JNU-SWCU/oss-hub/pull/1151) | Sign in or simulate each relevant role, open the destructive surface, and observe whether unauthorized roles can see or activate the action. | Gate the action by authority and expose only the authorized role's safe alternatives. |
| Continuity under loading | Preserve input focus and task context while asynchronous loading updates a surface. | Typing one character replaces the page with a skeleton so the next character cannot enter the field. | [oss-hub #1143](https://github.com/JNU-SWCU/oss-hub/pull/1143) | Focus an input, trigger its loading state by typing or submitting, and confirm focus, entered text, and surrounding context remain usable. | Keep the interactive shell mounted and update only the loading region. |
| Deep-link arrival | Land a shared deep link at its promised destination after asynchronous layout settles. | Opening a `#activity` link leaves the user at the page top. | [oss-hub #1141](https://github.com/JNU-SWCU/oss-hub/pull/1141) | Open the URL with its fragment in a fresh session, wait for asynchronous content, and observe the target in the viewport. | Retry or defer fragment scrolling after the target mounts and layout stabilizes. |
| Copy–validation parity | Make visible guidance match the validation rule that actually accepts or rejects input. | The UI permits or promises 50 MiB while the server rejects files over 5 MiB. | [oss-hub #1130](https://github.com/JNU-SWCU/oss-hub/pull/1130) | Read the visible limit, submit values immediately below and above it, and compare each result with the stated rule. | Derive copy and client validation from the canonical server constraint. |
| One canonical route per task | Give each task one canonical route instead of role-specific URL branches. | `/status` and `/mydocs` split one document task that belongs at `/documents`. | [oss-hub #1123](https://github.com/JNU-SWCU/oss-hub/pull/1123) | Reach the same task from each role and navigation entry, then observe whether each resolves to one canonical URL. | Consolidate the task at one route and branch content or permissions within it. |
| No lost state across substeps | Keep state throughout a multi-step flow inside one coherent shell. | Team creation, joining, solo selection, summary, and consent each restart the journey on separate paths. | [oss-hub #1171](https://github.com/JNU-SWCU/oss-hub/pull/1171) | Complete a substep, move forward and back, and confirm entered choices and progress survive every transition. | Use one flow shell with explicit step state and resumable transitions. |
| Role-task minimal action | Expose only the one action the operator needs for the assigned task. | A care worker sees an extra “해결 완료” action when confirmation alone completes the task. | SeeON-Front session (2026-08-13) | Enter the role's task, identify its completion criterion, and count whether each visible primary action is necessary to complete it. | Remove the extra action and retain the single role-appropriate confirmation control. |
